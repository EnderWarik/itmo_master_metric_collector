## ВВЕДЕНИЕ

В рамках производственной, технологической практики выполнено развёртывание инструментального стенда для автоматизированного сбора и сравнения метрик производительности веб-приложений. Стенд разработан в ходе преддипломной практики и служит основным инструментом получения экспериментальных данных для выпускной квалификационной работы по теме «Сравнительный анализ производительности микрофронтенд-архитектуры и монолитного фронтенда».

Объектом практики является программный стенд, обеспечивающий воспроизводимое измерение показателей производительности веб-приложений: времени загрузки страниц, метрик Lighthouse, характеристик выполнения JavaScript и поведенческих показателей пользовательских сценариев. Предметом практики выступают архитектурные и технологические решения, обеспечивающие контейнеризацию сервисов стенда, автоматическое развёртывание при помощи CI/CD-конвейера и использование отечественных платформ в процессе поставки программного обеспечения.

Цель работы — организовать производственное развёртывание стенда сбора метрик с настройкой автоматического CI/CD-конвейера на отечественной платформе.

Решение развёртывается как набор контейнеров под управлением Docker Compose, где серверная часть обеспечивает запуск браузера и сбор метрик, а клиентская часть предоставляет интерфейс для управления замерами и просмотра результатов. В отчёте последовательно рассматриваются анализ вариантов развёртывания с обоснованием выбора отечественных инструментов, проектирование процесса сбора метрик, контейнеризация компонентов стенда, настройка CI/CD-конвейера и результаты развёртывания на производственном сервере.

## 1 Анализ вариантов развёртывания с использованием отечественных разработок

### 1.1 Обзор доступных платформ

При выборе платформы для размещения репозитория и организации CI/CD-конвейера рассматривались варианты, удовлетворяющие требованию использования отечественных или импортозамещённых разработок.

В части платформ для хостинга Git-репозитория и организации CI/CD были рассмотрены следующие решения.

**GitVerse** (gitverse.ru) — российская платформа для хостинга кода, разработанная при участии Сбера. Предоставляет функциональность, аналогичную GitHub и GitLab: управление репозиториями, запросы на слияние, систему задач и встроенный CI/CD-конвейер на основе синтаксиса, совместимого с GitHub Actions. Платформа зарегистрирована в РФ, данные хранятся на российских серверах.

**Gitflic** (gitflic.ru) — отечественная платформа хостинга кода с поддержкой CI/CD-пайплайнов, ориентированная преимущественно на корпоративный сегмент.

В части облачных провайдеров для размещения сервисов рассматривались Яндекс Cloud, VK Cloud и Selectel как российские платформы, предоставляющие виртуальные серверы, управляемые кластеры Kubernetes и реестры контейнерных образов.

### 1.2 Обоснование выбора

По результатам анализа для хостинга репозитория и организации CI/CD выбрана платформа **GitVerse**. Основания для выбора:

- платформа является отечественной разработкой и удовлетворяет требованию импортозамещения;
- синтаксис CI/CD-пайплайнов совместим с GitHub Actions, что исключает необходимость изучения нового формата конфигурации;
- платформа предоставляет бесплатный доступ для открытых репозиториев;
- поддерживается подключение self-hosted runners, что позволяет выполнять сборку и деплой непосредственно на целевом сервере.

В качестве целевой среды развёртывания используется существующий виртуальный сервер (VPS) провайдера Aeza с характеристиками: 4 vCPU, 4 GB RAM, 10 GB SSD, ОС Ubuntu 22.04. Перенос на облачную платформу признан нецелесообразным ввиду наличия работающей производственной среды.

Использование внешнего реестра контейнерных образов также признано избыточным: поскольку сборка и запуск образов осуществляются на одном сервере, образы не требуют передачи по сети.

### 1.3 Итоговая схема развёртывания

Выбранная схема развёртывания выглядит следующим образом: при каждом коммите в основную ветку репозитория на GitVerse автоматически запускается CI/CD-конвейер, который на целевом сервере выполняет получение актуальной версии кода, сборку контейнерных образов и перезапуск сервисов.

```
push в ветку main
    → GitVerse CI (act runner, self-hosted на VPS)
        → git pull
        → docker compose build metrics-backend
        → docker compose build metrics-frontend
        → docker compose up -d
            → VPS 91.186.212.172
                ├── Traefik (reverse proxy, TLS)
                ├── metrics-backend (NestJS + Chromium)
                └── metrics-frontend (Vue 3, nginx)
```

## 2 Проектирование процесса сбора метрик

### 2.1 Назначение и состав стенда

Разработанный стенд представляет собой веб-приложение, предназначенное для автоматизированного измерения показателей производительности произвольных веб-страниц. Стенд состоит из двух сервисов.

**Серверная часть** реализована на платформе NestJS (Node.js) и выполняет следующие функции: управление сеансом браузера Chromium через протокол Chrome DevTools Protocol (CDP), запуск аудитов Lighthouse, сбор метрик Navigation Timing API, V8 и сетевых ресурсов, агрегация результатов нескольких повторных замеров и предоставление HTTP API для клиентской части.

**Клиентская часть** реализована на Vue 3 с использованием сборщика Vite и предоставляет пользовательский интерфейс для задания параметров замера (URL, количество повторов, включение E2E-сценария), просмотра результатов в табличном виде, сравнения двух URL с вычислением относительных отклонений и экспорта данных в формат CSV.

### 2.2 Методология измерений

Каждый замер выполняется в воспроизводимых условиях: viewport 1920×1080, кэш браузера отключён (режим инкогнито), сетевое замедление не применяется. Для снижения влияния случайных отклонений каждый сценарий запускается несколько раз (по умолчанию 10), после чего вычисляются медиана и среднее значение.

Замеры разделяются на холодные (первый запуск, DNS-записи не закешированы) и тёплые (повторные запуски с прогретым DNS). Разделение обусловлено тем, что при загрузке нескольких микрофронтендов с разных доменов первый запуск несёт дополнительные задержки DNS-разрешения, не характерные для последующих обращений.

### 2.3 Собираемые метрики

В рамках каждого замера собираются следующие группы метрик.

**Navigation Timing** — время DOM-парсинга, время выполнения синхронных скриптов, момент наступления событий DOMContentLoaded и Load.

**Lighthouse** — Speed Index, First Contentful Paint (FCP), Largest Contentful Paint (LCP), Time to Interactive (TTI), Total Blocking Time (TBT), Cumulative Layout Shift (CLS), итоговый показатель Performance Score.

**Ресурсы и сеть** — общее количество запросов, суммарный объём переданных данных, количество скриптов, число уникальных доменов.

**V8 и рендеринг** — время парсинга и компиляции JavaScript, суммарная длительность задач, количество операций Layout и Recalc Style, объём занятой памяти JS Heap.

**E2E-сценарий** — полное время выполнения пользовательского сценария (выбор позиции, оформление заказа), средняя и максимальная задержка отклика на ввод.

## 3 Контейнеризация проекта

### 3.1 Общая структура

Проект контейнеризирован с использованием Docker и Docker Compose. Для каждого сервиса описан отдельный Dockerfile с многоступенчатой сборкой, что позволяет минимизировать размер финальных образов: в производственный образ включаются только скомпилированные артефакты и зависимости времени выполнения, сборочные инструменты в него не попадают.

Оркестрация сервисов осуществляется через файл `docker-compose.prod.yml`, описывающий три контейнера: reverse proxy Traefik, серверную часть и клиентскую часть.

### 3.2 Контейнеризация серверной части

Серверная часть собирается в четыре стейджа.

Стейдж `base` формирует общий базовый образ на основе `node:20-slim`. На этом же уровне выставляются переменные окружения `PUPPETEER_SKIP_DOWNLOAD=true` и `PUPPETEER_SKIP_CHROMIUM_DOWNLOAD=true`, которые предписывают Puppeteer не загружать собственную копию браузера ни на одном из последующих стейджей сборки. Это критически важно: без данных переменных Puppeteer при установке зависимостей пытается скачать Chrome (~170 МБ), что приводит к ошибкам при сборке в ограниченной среде.

Стейдж `deps` выполняет установку зависимостей (`npm ci`). Стейдж `builder` компилирует TypeScript-исходники в JavaScript (`npm run build`).

Финальный стейдж `runner` формирует производственный образ. В него устанавливается системный браузер Chromium из репозиториев Debian (`apt-get install -y chromium`). Переменная `PUPPETEER_EXECUTABLE_PATH=/usr/bin/chromium` направляет Puppeteer на использование системного браузера. Из сборочного стейджа копируются только скомпилированный код (`dist/`) и производственные зависимости.

Использование системного Chromium вместо Google Chrome обусловлено следующим: пакет `chromium` доступен в стандартных репозиториях Debian без необходимости подключения сторонних источников и дополнительной верификации ключей; при повторных сборках слой с Chromium кешируется Docker и не загружается заново при изменениях в коде приложения.

### 3.3 Запуск Chromium в контейнере

Headless-браузер в контейнерной среде требует дополнительных привилегий. В `docker-compose.prod.yml` для сервиса серверной части указаны следующие параметры:

- `cap_add: SYS_ADMIN` — необходимо для работы механизма sandbox браузера;
- `security_opt: seccomp:unconfined` — отключает профиль seccomp, ограничивающий системные вызовы, часть из которых требуется Chromium;
- `shm_size: 2gb` — увеличивает размер разделяемой памяти, используемой браузером для рендеринга.

Без перечисленных настроек Chromium завершает работу с ошибкой при попытке создать изолированный процесс рендеринга.

### 3.4 Контейнеризация клиентской части

Клиентская часть собирается в три стейджа. Стейджи `base` и `builder` устанавливают зависимости и выполняют сборку статических файлов. Адрес API серверной части передаётся через аргумент сборки `VITE_API_URL`, что позволяет использовать один и тот же Dockerfile для разных окружений.

Финальный стейдж `runner` основан на образе `nginx:1.27-alpine` и содержит только скомпилированные статические файлы. Это делает образ клиентской части минималистичным: размер финального образа не превышает 30 МБ.

### 3.5 Оркестрация и reverse proxy

Файл `docker-compose.prod.yml` описывает три сервиса в общей сети `metric`.

**Traefik** выступает в роли reverse proxy и точки входа. Он автоматически получает и обновляет TLS-сертификаты Let's Encrypt через HTTP-challenge, маршрутизирует запросы к `/api` на серверную часть, остальные запросы — на клиентскую часть. Маршруты объявляются через Docker-метки (`labels`) непосредственно в описании сервисов, что позволяет Traefik автоматически обнаруживать конфигурацию без изменения собственных файлов настроек.

### 3.6 Инструкция по развёртыванию

Для развёртывания стенда вручную необходим сервер с установленными Docker Engine версии 24 и выше и Docker Compose v2, а также открытыми портами 80 и 443.

```bash
# Клонировать репозиторий
git clone https://gitverse.ru/EnderWar/itmo_master_metric_pizza_collector.git
cd itmo_master_metric_pizza_collector

# Собрать образ серверной части
docker compose -f docker-compose.prod.yml build metrics-backend

# Собрать образ клиентской части
docker compose -f docker-compose.prod.yml build metrics-frontend

# Запустить все сервисы
docker compose -f docker-compose.prod.yml up -d

# Проверить статус контейнеров
docker compose -f docker-compose.prod.yml ps
```

Для локального запуска без TLS используется базовый `docker-compose.yml`:

```bash
docker compose up -d
# Клиентская часть: http://localhost:8080
# API серверной части: http://localhost:3000/api
```

## 4 Развёртывание с использованием CI/CD

### 4.1 Подключение self-hosted runner

GitVerse CI использует модель self-hosted runners: для выполнения заданий пайплайна необходимо зарегистрировать и запустить агент на целевом сервере. Это решение архитектурно оправдано для данного проекта: runner выполняется непосредственно на production-сервере, что исключает необходимость передачи артефактов по сети и организации SSH-доступа из среды CI.

GitVerse предоставляет собственную реализацию act runner, совместимую с форматом Gitea Actions. Установка выполняется следующим образом:

```bash
# Создать директорию для runner
mkdir gitverse-runner && cd gitverse-runner

# Загрузить бинарный файл runner
curl -o act_runner_linux_amd64 -L \
  https://gitverse.ru/api/packages/gitverse/generic/act_runner_linux_amd64/5.2.0/act_runner_linux_amd64

chmod +x act_runner_linux_amd64

# Зарегистрировать runner (токен получается в Settings → Runners репозитория)
./act_runner_linux_amd64 register --no-interactive \
  --instance https://gitverse.ru/sc \
  --token <REGISTRATION_TOKEN> \
  --name my_runner
```

Открыть: GitVerse → репозиторий → Settings → Runners]

### 4.2 Запуск runner как системного сервиса

Для обеспечения автоматического запуска runner при перезагрузке сервера и его восстановления при аварийном завершении runner зарегистрирован как systemd-сервис. Конфигурационный файл `/etc/systemd/system/gitverse-runner.service`:

```ini
[Unit]
Description=GitVerse Act Runner
After=network.target

[Service]
WorkingDirectory=/root/gitverse-runner
ExecStart=/root/gitverse-runner/act_runner_linux_amd64 daemon
Restart=always
RestartSec=5
Environment=HOME=/root

[Install]
WantedBy=multi-user.target
```

```bash
systemctl daemon-reload
systemctl enable gitverse-runner
systemctl start gitverse-runner
```

Директива `Restart=always` гарантирует перезапуск процесса при любом завершении. Переменная `Environment=HOME=/root` необходима для корректного определения рабочих путей runner в контексте systemd, где домашняя директория пользователя не устанавливается автоматически.

[СКРИНШОТ 5: Вывод команды `systemctl status gitverse-runner` на сервере — сервис в статусе active (running).
Выполнить на сервере: systemctl status gitverse-runner]

### 4.3 CI/CD-пайплайн

Конфигурация пайплайна располагается в файле `.gitverse/workflows/deploy.yml`. Пайплайн запускается при каждом коммите в ветку `main` и выполняет четыре шага последовательно.

```yaml
name: Deploy to Production

on:
  push:
    branches:
      - main

jobs:
  deploy:
    runs-on: self-hosted

    steps:
      - name: Pull latest code
        run: |
          REPO_URL="https://${{ secrets.VCS_TOKEN }}@gitverse.ru/EnderWar/..."
          DEPLOY_DIR="/root/metrics"
          if [ -d "$DEPLOY_DIR/.git" ]; then
            cd "$DEPLOY_DIR"
            git remote set-url origin "$REPO_URL"
            git pull origin main
          else
            rm -rf "$DEPLOY_DIR"
            git clone "$REPO_URL" "$DEPLOY_DIR"
          fi

      - name: Build backend
        run: cd /root/metrics && docker compose -f docker-compose.prod.yml build metrics-backend

      - name: Build frontend
        run: cd /root/metrics && docker compose -f docker-compose.prod.yml build metrics-frontend

      - name: Start containers
        run: cd /root/metrics && docker compose -f docker-compose.prod.yml up -d
```

Шаг `Pull latest code` получает актуальную версию кода из репозитория. При первом запуске выполняется клонирование, при последующих — обновление существующего репозитория. Токен доступа передаётся через секрет `VCS_TOKEN`, хранящийся в настройках репозитория, и не фиксируется в истории коммитов.

Шаги `Build backend` и `Build frontend` выполняют сборку образов последовательно во избежание конкуренции за ресурсы сервера при параллельной сборке. Docker кеширует слои образов: при отсутствии изменений в Dockerfile повторная сборка занимает секунды.

Шаг `Start containers` перезапускает сервисы командой `up -d`, которая пересоздаёт только те контейнеры, образы которых изменились.

### 4.4 Управление секретами

Для аутентификации при получении кода с GitVerse в настройках репозитория (Settings → Secrets) хранится секрет `VCS_TOKEN` — персональный токен доступа. Токен передаётся runner через переменную окружения и используется только в рамках текущего сеанса выполнения задания, не сохраняясь на диске сервера.

## ЗАКЛЮЧЕНИЕ

В ходе производственной практики выполнено развёртывание инструментального стенда для сбора метрик производительности веб-приложений с настройкой автоматического CI/CD-конвейера на отечественной платформе.

Проведён анализ доступных отечественных платформ для хостинга кода и организации CI/CD. По результатам анализа выбрана платформа GitVerse как российская разработка с поддержкой совместимого с GitHub Actions синтаксиса пайплайнов и возможностью подключения self-hosted runners.

Оба компонента стенда — серверная часть на NestJS и клиентская часть на Vue 3 — контейнеризированы с использованием многоступенчатых Dockerfile. Серверный образ включает системный браузер Chromium с необходимыми привилегиями для запуска в контейнерной среде. Оркестрация сервисов осуществляется через Docker Compose с Traefik в роли reverse proxy, обеспечивающего автоматическое получение TLS-сертификатов.

Настроен self-hosted runner GitVerse CI, зарегистрированный как systemd-сервис для обеспечения непрерывной доступности. Разработан пайплайн, автоматически выполняющий получение актуального кода, последовательную сборку образов и перезапуск контейнеров при каждом коммите в основную ветку.

Развёрнутое приложение доступно по адресу https://metric.pizza.ew-production.ru и активно используется для проведения экспериментов в рамках выпускной квалификационной работы.
