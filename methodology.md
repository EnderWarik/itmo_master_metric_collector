# Методика проведения измерений и обработки результатов

## 1. Инфраструктура тестирования

### 1.1. Сервер сбора метрик

Сервис сбора метрик развёрнут на выделенном сервере:

| Параметр | Значение |
|----------|----------|
| **RAM** | 4 GB |
| **CPU** | 1 ядро |
| **Сеть** | до 300 Мбит/с |
| **Регион** | Швеция |
| **ОС** | Linux (Docker) |
| **Браузер** | Chromium (headless) |

**Компоненты:**
- **Backend** (NestJS) — оркестрация сбора метрик
- **Puppeteer** — headless браузер для browser-метрик
- **Lighthouse** — аудит Web Vitals
- **Chrome DevTools Protocol (CDP)** — низкоуровневые метрики V8

---

### 1.2. Серверы приложений (тестируемые сайты)

Оба варианта архитектуры (Монолит и Микрофронтенды) развёрнуты на идентичных серверах:

| Параметр | Значение |
|----------|----------|
| **RAM** | 2 GB |
| **CPU** | 1 ядро |
| **Сеть** | до 25 Гбит/с |
| **Количество серверов** | 2 (монолит + MFE) |

**Конфигурация:**
- **Nginx** — reverse proxy, статика, gzip/brotli сжатие
- **Docker** — контейнеризация приложений
- **HTTP/2** — включён для всех ресурсов

## 2. Процесс сбора метрик

│  │   Metrics   │  │   Metrics   │  │      Scenarios      │  │
│  │             │  │             │  │                     │  │
│  │ • Ping      │  │ • DOM       │  │ • Симуляция         │  │

---

### 2.2. Последовательность замера

Для каждого URL выполняется следующая последовательность:

1. **Ping** — HTTP GET запрос, измерение времени отклика
2. **TTFB** — детальный замер фаз соединения (DNS, TCP, TLS, Server)
3. **Navigation Timing** — полная загрузка страницы через Puppeteer
4. **Resource Timing** — анализ загруженных ресурсов + CDP метрики V8
5. **Lighthouse** — аудит Web Vitals (FCP, LCP, TTI, TBT, CLS)
6. **FPS** — измерение частоты кадров в покое (3 секунды)
7. **E2E** — выполнение сценария взаимодействия (опционально)

---

### 2.3. Условия замера

| Параметр | Значение |
|----------|----------|
| **Кэш браузера** | Отключён (incognito mode) |
| **Throttling** | Отключён (реальные условия сети) |
| **Viewport** | 1920×1080 (Desktop) |
| **User-Agent** | Chrome (headless) |
| **Ожидание загрузки** | `networkidle0` (нет сетевых запросов 500мс) |
| **Стабилизация** | 500-1000мс после загрузки перед замером |

## 3. Обработка результатов

### 3.1. Агрегация данных

Для статистической значимости рекомендуется:

| Метод | Применение |
|-------|------------|
| **Медиана** | Основной показатель (устойчив к выбросам) |
| **Среднее** | Для сравнения с медианой |
| **P95** | Выявление проблемных случаев |
| **Min/Max** | Границы разброса |
| **N замеров** | ≥5 для каждого URL |

---

### 3.2. Группировка метрик для сравнения

#### Сетевые метрики
- `ttfbMs` — время до первого байта
- `totalTransferSize` — объём переданных данных
- `http2Percent` — использование HTTP/2
- `cacheHitPercent` — эффективность кэширования

#### Метрики загрузки
- `domContentLoadedMs` — готовность DOM
- `loadEventMs` — полная загрузка
- `fcpMs`, `lcpMs` — Core Web Vitals

#### Метрики рантайма
- `scriptDurationMs` — время выполнения JS
- `jsHeapUsedSize` — потребление памяти
- `avgFps`, `minFps` — плавность анимаций

#### Метрики интерактивности
- `ttiMs` — время до интерактивности
- `tbtMs` — блокировка main thread
- `avgInputDelayMs` — задержка ввода (E2E)

---

### 3.3. Специфичные метрики для MFE-сравнения

| Метрика | Монолит | MFE | Что показывает |
|---------|---------|-----|----------------|
| `chunkedJsCount` | Меньше (~10-20) | Больше (~30+) | Уровень code-splitting |
| `largestChunkSize` | Большой (500KB+) | Меньше (<200KB) | Размер начальной загрузки |
| `uniqueDomains` | 1-2 | 3+ | Количество источников ресурсов |
| `scriptsCount` | Меньше | Больше | Количество JS файлов |

## 4. Ограничения методики

### 4.1. Network-related ограничения

- **Географическое расположение**: Сервер метрик в Швеции — результаты репрезентативны для европейских пользователей
- **Сетевая латентность**: ~50-100мс RTT между серверами (реальные условия)
- **Bandwidth**: 300 Мбит/с достаточно для загрузки современных SPA

### 4.2. Browser-related ограничения

- **Headless режим**: Может отличаться от реального браузера на ~5-10%
- **Lighthouse throttling**: Отключён для реальных условий (не симуляция 3G)
- **Один поток**: 1 CPU ядро может влиять на CPU-интенсивные метрики

### 4.3. Что НЕ измеряется

- **RUM (Real User Monitoring)** — реальные пользователи не участвуют
- **FID (First Input Delay)** — заменён на `inputDelayMs` через E2E симуляцию
- **INP (Interaction to Next Paint)** — частично покрывается E2E метриками
- **CrUX данные** — требуют реального трафика

## 5. Воспроизводимость

Для воспроизведения результатов:

```bash
# 1. Запуск сервиса метрик
docker-compose -f docker-compose.prod.yml up -d

# 2. Сбор метрик через API
curl -X POST http://localhost:3000/api/metrics/collect \
  -H "Content-Type: application/json" \
  -d '{"url": "https://target-site.com"}'

# 3. E2E сценарий
curl -X POST http://localhost:3000/api/metrics/e2e \
  -H "Content-Type: application/json" \
  -d '{
    "scenario": {
      "name": "User Flow",
      "url": "https://target-site.com",
      "steps": [
        {"action": "click", "selector": "#login-btn"},
        {"action": "type", "selector": "#email", "value": "test@test.com"}
      ]
    }
  }'
```
